Summary This process enables a field officer or authorised user to create or modify a loan enquiry by submitting all required customer, asset, and financial information — along with supporting KYC documents — through a mobile or online channel. Upon receipt of the submission, the process authenticates the requesting user and their device, validates the completeness and format of all input data, and performs a series of ordered business validations: it checks the applicant's identity documents against caution and de-duplication databases, verifies that the applicant's geography falls within the branch's service area, confirms that product and eligibility rules are satisfied (including NRI restrictions, GECL blocks, and deceased-customer checks), and validates the asset cost and model year. Once all validations pass, the process creates or updates the enquiry record in the system, assigns a unique system-generated enquiry number, records all applicant details, dispatches consent and confirmation messages where applicable, initiates fraud screening and credit bureau requests, uploads any KYC document images to the document management system, links the enquiry to any originating lead management record, and returns the final enquiry number and asset cost advisory to the caller. Business purpose: Create a validated, fully recorded loan enquiry that can proceed to formal application assessment, or update an existing enquiry with revised data. Triggered by: A field officer, marketing employee, or authorised system user submitting loan enquiry details via a mobile or web interface. Accepts document upload: Yes — a compressed archive of KYC images (photographs, identity documents) is accepted alongside the enquiry data. Input summary: User credentials and device identifiers; processing mode (create or modify); enquiry date and existing enquiry number (for modification); contract and product details; asset details; one or more applicant records containing personal, address, identity document, and communication details; GPS location; and an optional lead management system reference. Output summary: A system-generated enquiry number, a success or failure status with descriptive message, an asset cost advisory message where the system price has been updated, and credit bureau and fraud check status indicators. Key supporting operations: User and device authentication — validates the requesting user's identity and device registration against the system registry. Branch determination — resolves the user's assigned branch from employee records. KYC validation and de-duplication — checks identity document formats, caution lists, and external de-duplication services for each applicant. Geographic validation — verifies that the applicant's pincode falls within the branch's permitted service radius or is explicitly mapped to the branch. Product model market value retrieval — fetches the current state-level dealer price for the selected product model, overriding the submitted asset cost where applicable. Appraisal category validation — confirms that the selected assessment category is valid for the branch, contract type, and asset cost. Enquiry number generation — assigns a unique, sequentially controlled document number following a defined format. Fraud screening — submits the enquiry to Hunter and Sherlock fraud detection services and interprets their results. Credit bureau request — initiates a CIBIL credit report request for individual applicants. Document image upload — encodes and transmits KYC images to the document management system under the enquiry reference. Lead management linkage — if an originating lead record exists, updates it with the newly generated enquiry number. Notification and communication — sends SMS consent messages to applicants, internal alert emails to branch teams, and system notifications to marketing employees. Caution list post-check — after saving, screens all applicants against an internal caution database. http_method: POST 2. High-Level Functional Requirements The process must authenticate the user and validate their device before processing any enquiry data. The process must accept and parse a structured set of loan enquiry details, including contract information and one or more applicants. The process must validate all submitted data against a comprehensive set of business rules, including mandatory field checks, data format validations, and complex eligibility criteria. The process must perform de-duplication checks for all applicants using various KYC identifiers (e.g., PAN, Aadhaar) to prevent duplicate entries and identify existing customers. The process must check all applicants against internal caution lists to mitigate risk. The process must enforce product-specific rules, such as eligibility criteria for NRI applicants or restrictions on certain contract types. The process must enforce geographical constraints, including validating that an applicant's location is serviceable by the user's branch. The process must generate a unique, sequential enquiry number for each new, successfully validated loan enquiry. The process must create or modify loan enquiry and applicant records, persisting all validated information. The process must handle the upload of a compressed file containing KYC documents, extract each document, and submit it to a document management system with appropriate metadata. The process must be able to trigger subsequent automated actions, such as fraud detection checks (Hunter/Sherlock) and credit bureau requests, upon successful enquiry creation. The process must provide clear feedback to the user, returning a success message with the enquiry number or a specific error message explaining the reason for rejection. 3. Consolidated Process Flow 4.1 Process Overview The Loan Enquiry Creation and Submission process receives a multipart request containing customer, product, and document data from a field officer operating via a mobile or online channel. It authenticates the requesting user and device, applies a comprehensive sequence of business validations spanning identity, geography, product eligibility, and data integrity, persists the enquiry and applicant records, and returns a unique enquiry number that identifies the record for all downstream processing. When operating in modify mode, the process re-validates all data and refreshes the existing enquiry record. The process is designed to be self-contained: it generates its own enquiry numbers, handles its own document uploads, and initiates downstream fraud and credit checks before returning control to the caller. 4.2 End-to-End Process Flow Step 1: User and Device Authentication The process receives the user identifier and device credentials. If the primary device identifier is blank, the secondary device identifier is substituted. The authentication service is invoked to verify that the user is active in the system registry and that the device is authorised. The service checks the user's status and returns it as part of a delimited result string. If the user status is not 'Active', or if the authentication service returns an error, the process immediately returns a failure response to the caller with the reason provided by the authentication service. No further processing occurs. Step 2: Input Completeness Check The processing mode indicator is trimmed of whitespace. The enquiry input details field is trimmed; if it is blank after trimming, it is treated as absent. If the enquiry input details are absent, the process returns a failure response indicating that the input values are required. Step 3: Branch Resolution The user's assigned branch is retrieved from the employee register by matching the user identifier (left-padded to 6 characters) to the employee record. The branch code resolved here is used in all subsequent geographic, product, and enquiry-saving operations. Step 4: Enquiry Date Parsing The enquiry date string is parsed into a date value using the DD/MM/YYYY format. If the date string cannot be parsed, an exception is raised and the process terminates with an error. Step 5: Contract Details Extraction The enquiry input details JSON is parsed. The contract details sub-object is located. If the contract type field is absent from the contract details, the process returns a failure response indicating that the contract type is required. When present, all contract-level fields are extracted: asset make, asset type, asset cost, contract type, asset class, business source, loan purpose, marketing employee, finance amount, loan tenure, number of units, asset model, remarks, assessment criteria, employment years, net income, asset usage, experience in years, quoted interest rate, residence pincode, residence location, location stability years, dealer code, appraisal category, fuel type, tractor ownership details, land holdings, agricultural indicator, repayment frequency, horsepower, and product model. Step 6: Enquiry Number Extraction (Modify Mode) If the input contains an 'enquiry_number' sub-object with a value, that value is extracted and held as the enquiry number to be modified. This is only relevant when operating in modify mode. Step 7: Applicant Details Extraction and Preparation The applicant list is iterated. For each applicant record: the applicant type is extracted and normalised (characters after a hyphen-separator are removed); the applicant is classified as 'MAIN APPLICANT' or 'ADDL APPLICANT - N' based on the presence of 'ADDL APPLICANT' in the type; the customer code presence determines whether the applicant is flagged as existing or new; the gender value is normalised to 'M' (Male) or 'F' (Female); the date of birth is parsed from DD/MM/YYYY if provided; the passport validity date is parsed similarly and set to null if absent; all KYC document numbers, contact details, and preference flags are extracted; the SMS indicator is derived by evaluating the enquiry decision indicator — if 'N' the SMS indicator is cleared, if 'Y' and no SMS indicator is set it defaults to 'N'; the PAN exemption declaration number is processed to determine whether a PAN exemption flag should be set; and any modification override for the SMS indicator is applied from the modify-details sub-object if one exists for the same applicant type. Each prepared applicant record is added to the full applicant collection, and those flagged as 'NEW' (based on the SMS send indicator) are also added to the modify-specific collection. Step 8: Customer vs. Contract Code Resolution For each applicant that has a provided customer/contract code, the system queries the customer and contract registers to determine whether the code refers to a customer record or a contract record. If it refers to a contract, the contract number is stored separately and the associated customer code is retrieved and used in its place. This ensures that the applicant record is always linked to the canonical customer identifier. Step 9: Gender Normalisation for Non-Individual Applicants If the applicant's constitution type is 'NON INDIVIDUAL', the gender field is cleared, as gender is not applicable to corporate or partnership applicants. Step 10: Main Applicant Location Recording The location record identifier of the main applicant is preserved for use in the product model price retrieval step. Step 11: Aadhaar Number Validation The Aadhaar number from the last-processed applicant is subjected to a Verhoeff algorithm check. The algorithm reverses the digit array and applies a permutation table and a multiplication table to compute a check value. If the computed check value is not zero, the Aadhaar number is invalid. The process rolls back any partial changes, and returns a failure response indicating an invalid Aadhaar number. Step 12: KYC De-duplication and Caution Check The KYC details of all applicants are submitted for de-duplication and caution screening. For each applicant: any previously stored KYC data is compared against the newly submitted data to detect changes; an attempt is made to find an existing customer record using the customer code and PAN; if a PAN is present, it is validated against the internal caution and block list — if the PAN status is anything other than 'Allowed', the process halts with an error; for each non-null identity document (PAN, Driving Licence, Passport, Voter ID, Aadhaar), the document format is validated, and a de-duplication check is performed against existing enquiry and application records — if a confirmed duplicate is found linked to a pending or active application, the process halts; for individual applicants, the PAN is also submitted to an external de-duplication service (unless the enquiry originates from a recognised OEM source), and confirmed duplicates halt the process while soft warnings are recorded; Aadhaar numbers for individual applicants are checked to be exactly 12 digits; GECL contract checks are performed if the system parameter is enabled; and mobile numbers are validated for format correctness. If any check fails, the process rolls back and returns the error to the caller. Step 13: Enquiry Data Comprehensive Validation The full set of enquiry data is submitted to the comprehensive validation routine. This routine: validates that the asset model year falls within the permitted range calculated from the current year and system parameters (for asset category 1); confirms the asset cost is greater than zero and not less than the finance amount; checks if the user has access to the Vruddhi channel and, if so, blocks creation of designated contract types outside that channel; validates each applicant's mobile number format and performs an external PAN de-duplication API call for non-OEM enquiries; checks for GECL contract blocks; confirms no applicant is marked as deceased; and enforces NRI-specific rules requiring valid passport details (not expired, valid for at least 90 more days), alternate mobile number, and email address, and restricting NRI applicants to the permitted product combination only. If any validation fails, the process rolls back and returns the error. Step 14: Contact Cross-Branch Validation (Save Indicator = N, Existing Main Applicant) When the save indicator signals that a pre-save validation pass is required, and the current applicant is an existing main applicant, the system checks whether the applicant has active enquiries at other branches. If informational warnings are returned, they are collected for inclusion in the subsequent pincode validation response. Step 15: Pincode-to-Branch Geographic Validation For each applicant, if an applicant type has been established, the applicant's pincode and location are validated against the branch's geographic service area. The system determines the distance between the applicant's location and the branch. If the distance exceeds the branch's configured maximum, the system checks whether the pincode is explicitly mapped to the branch in the override table. Validation is bypassed for SME branches, for users holding the designated bypass access right, and for enquiries or contracts on the explicit exclusion list. If the pincode is not mapped to the branch and no bypass applies, an informational warning (for the mobile channel component) or a hard error (for other components) is returned. If both a pincode error and a contact cross-branch warning exist, they are combined into a single response. The process returns this response with a save-allowed indicator of 'Y', signalling to the caller that saving is conditional. Step 16: Product Model Market Value Retrieval The current dealer price for the product model is retrieved based on the contract type, asset class, dealer code, main applicant location, product model identifier, and quantity. If an error is returned, the process rolls back and returns a failure. If a market value is returned, it replaces the previously extracted asset cost, and an advisory message is prepared to inform the caller that the asset cost has been updated to the current state-level price. Step 17: Appraisal Category Validation The selected appraisal category is validated against the branch, contract type, asset class, updated asset cost, and enquiry date. If the combination is not valid, the process rolls back and returns a failure response. Step 18: Enquiry Record Creation or Modification The process invokes the enquiry persistence routine, passing all validated contract and applicant data along with the processing mode. This routine: validates the branch is active; validates the user exists; enforces Vruddhi channel restrictions; invokes branch-level enquiry blocking checks (pending aged enquiries, maximum pending days for field officer and branch); calls the comprehensive data validation routine again as a final gate; determines the branch stage and Hunter service configuration; and then either creates a new enquiry record (assigning a system-generated number by calling the number generation function that locks a control record, increments it atomically, and constructs the number as prefix + 4-digit branch + 2-digit year + padded sequence) or updates the existing enquiry record. For creation, applicant records are inserted, PAN exemption declaration numbers are marked as used, and SMS consent messages are dispatched. For non-individual main applicants at single-stage branches, the enquiry is immediately set to Eligible for Application status. For modification, applicant records not yet sent a confirmation SMS are deleted and re-inserted. Fraud check results are re-evaluated: if Hunter and Sherlock results indicate clearance or manual approval, the enquiry advances to Eligible for Application; otherwise it remains Pending. Welcome communications are sent for newly eligible Hire Purchase enquiries. Internal alert emails are sent for pending enquiries at two-stage approval branches. The enquiry record is committed to the database. All applicants are screened against the caution database post-commit. Marketing employee notifications are dispatched when applicable. Step 19: Lead Management System Linkage If a lead management system reference was provided and is non-blank, the process calls the lead update routine to record the newly generated enquiry number against the originating lead record. If this call encounters an error, the error is logged but does not fail the overall transaction; a secondary commit is issued on success. Step 20: KYC Document Image Upload If the uploaded file is present and non-empty: the archive is saved to the configured temporary directory under a composite identifier built from the enquiry number and a timestamp; the document environment indicator and scan date are retrieved from the system parameter registry; the archive is unpacked and each entry is processed in turn; the document type is determined from the filename (photo, driving licence, or other KYC types); an XML metadata descriptor is constructed containing the enquiry number, branch, applicant type, customer name, document group, and document type; the image file is encoded to Base64; and the encoded image plus metadata are submitted to the document management service using the environment-appropriate service endpoint (test, beta, or live). Each successful upload returns a document index. After all entries are processed, the archive and temporary files are deleted. Step 21: Fraud Screening and Credit Bureau Initiation After successful enquiry creation, the system checks the system parameter to determine whether the online fraud screening service is active. If active, the Hunter and Sherlock fraud detection values for the enquiry are retrieved and evaluated: if both services are enabled and both return clear results, the fraud status is recorded as clear and the credit bureau service is called; if either returns a non-clear result, the fraud status message is set accordingly. If the online fraud service is not active, the system queries the enquiry for individual applicants and, if found, calls the credit bureau service directly. The credit bureau service constructs a parameterised request URL and makes an HTTP GET call; success is indicated by a 2xx response code. Regardless of the fraud screening outcome, a final credit bureau call is made in the cleanup phase if one has not already been recorded as having been called. Step 22: Response Construction and Resource Release A success response is built containing the status indicator ('1'), the message 'Success', the enquiry number, the enquiry response label, and the asset cost advisory message. All resources — database connections, file handles, temporary files — are released. If an uncaught exception occurred at any point, it is logged and the partial response built to that point is returned. 4.3 Process End States Enquiry Created Successfully A new enquiry record is persisted with a unique system-generated number, all applicant records are stored, KYC images are uploaded, fraud and credit checks are initiated, and a success response with the enquiry number is returned. Enquiry Modified Successfully An existing enquiry record is updated with revised data, changed applicant records are refreshed, any applicable notifications are dispatched, and a success response with the enquiry number is returned. Authentication Failure The user or device is not valid. No enquiry record is created. A failure response with the reason is returned to the caller. Mandatory Input Absent Required input fields are missing. No enquiry record is created or modified. A failure response specifying the missing information is returned. Aadhaar Validation Failure The Aadhaar number fails the Verhoeff check. Any partial transaction is rolled back. A failure response indicating an invalid Aadhaar number is returned. KYC De-duplication Failure An applicant's identity document is found to be on a caution list or is a confirmed duplicate against an active application. Any partial transaction is rolled back. A failure response with the specific error is returned. Comprehensive Data Validation Failure One or more business rules (asset cost, NRI eligibility, deceased customer, Vruddhi channel, etc.) are violated. Any partial transaction is rolled back. A failure response with the specific violation is returned. Geographic Validation Warning The applicant's pincode is outside the branch service area. The process returns a conditional response (status '3') with a save-allowed indicator of 'Y', allowing the caller to decide whether to proceed after acknowledging the warning. Product Model Price Override The system replaces the submitted asset cost with the current NDLP value. A success response is returned along with an advisory message that the asset cost has been updated. Fraud Screening Non-Clear Fraud screening returns a non-clear result. The enquiry is saved and the result status is returned to the caller; the enquiry remains in Pending status pending manual review. Enquiry Creation Processing Failure The backend persistence routine returns an error. Any partial transaction is rolled back. A failure response with the specific message is returned. Enquiry Number Generation Contention Another user holds a lock on the number control record. A failure response indicating the document number is in use is returned and no enquiry is created. 5.
